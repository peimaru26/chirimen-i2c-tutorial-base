# 工程4 成果物 — SGP30 ドライバー API 確定仕様

Example を先に書くことで確定した API。**工程5（Driver 作成）はこの仕様を満たすように実装する。**

## 実装スコープの決定

「全機能を実装する」のではなく、**実機で検証手順を書ける機能だけを実装する**方針を採った。
未検証のメソッドはレビュアーが妥当性を判断できず、無いメソッドより悪いという判断。

| 機能                | コマンド            | 採否       | 理由                                                                                                                                                                          |
| ------------------- | ------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Measure_air_quality | `0x2008`            | ✅ 採用    | アルコールを近づければ検証できる                                                                                                                                              |
| Get_serial_id       | `0x3682`            | ✅ 採用    | 毎回同じ非ゼロ値が出れば検証できる。疎通確認に有用                                                                                                                            |
| Measure_raw         | `0x2050`            | ✅ 採用    | 息を吹きかければ H2 が動く                                                                                                                                                    |
| Get/Set_baseline    | `0x2015` / `0x201E` | ✅ 採用    | **往復テスト**（get → 同値を set → get）で12時間待たずに検証できる                                                                                                            |
| Get_feature_set     | `0x202F`            | ⚙ 内部利用 | `init()` の疎通確認に使う。公開はしない                                                                                                                                       |
| Measure_test        | `0x2032`            | ❌ 見送り  | データシートに「`sgp30_iaq_init` の後には使うべきでない」「実行後はスリープモードに入る」と明記されており、`init()` 内での安全な配置に追加検証が必要                          |
| Set_humidity        | `0x2061`            | ❌ 見送り  | 補正が効いたかを外部から検証できない。絶対湿度換算と 8.8 固定小数点の理解コストに対して検証可能性がゼロ。実用には第2センサー（SHT30等）が必要で example が2デバイス構成になる |

## 確定した API

### `new SGP30(i2cPort, slaveAddress)`

| 引数           | 型      | 説明                                                  |
| -------------- | ------- | ----------------------------------------------------- |
| `i2cPort`      | I2CPort | `i2cAccess.ports.get(1)` で取得したポートオブジェクト |
| `slaveAddress` | Number  | `0x58` 固定。省略時のデフォルトも `0x58`              |

### `async init()`

I2C ポートを open し、疎通確認をしてから測定を開始できる状態にする。使用前に必ず 1 回実行する。

1. `i2cPort.open(slaveAddress)`
2. `0x202F`（Get feature set）で疎通確認 — **配線ミス・アドレス違いをここで検出する**
3. `0x2003`（Init air quality）で IAQ アルゴリズムを開始

### `async read()`

| 返り値   | 型     | 説明                                         |
| -------- | ------ | -------------------------------------------- |
| `o.eCO2` | Number | 二酸化炭素相当値。単位 **ppm**（400〜60000） |
| `o.tvoc` | Number | 総揮発性有機化合物。単位 **ppb**（0〜60000） |

`0x2008` 送信 → 12ms 待ち → 6バイト読み。並びは `[eCO2, CRC, TVOC, CRC]`（**eCO2 が先**）。

### `async readRaw()`

| 返り値      | 型     | 説明                                                    |
| ----------- | ------ | ------------------------------------------------------- |
| `o.h2`      | Number | H2 生信号（sout_H2）。単位はティック（無次元）          |
| `o.ethanol` | Number | エタノール生信号（sout_EtOH）。単位はティック（無次元） |

`0x2050` 送信 → 25ms 待ち → 6バイト読み。並びは **H2 → Ethanol**。
濃度への変換式はデータシートにあるが、生値のまま返して利用側に委ねる。

### `async readSerialNumber()`

48bit のシリアル番号を **12桁の小文字16進文字列**（例 `"000012345678"`）で返す。
数値ではなく識別子なので文字列で返す。`0x3682` 送信 → 10ms 待ち → 9バイト読み（3ワード）。

### `async getBaseline()`

| 返り値   | 型     | 説明                              |
| -------- | ------ | --------------------------------- |
| `o.eCO2` | Number | eCO2 のベースライン値（0〜65535） |
| `o.tvoc` | Number | TVOC のベースライン値（0〜65535） |

**ppm / ppb ではなくアルゴリズムの内部状態値**（不透明な16bit値）。`setBaseline()` に渡すためだけに使う。
`0x2015` 送信 → 10ms 待ち → 6バイト読み。応答の並びは **CO2eq → TVOC**。

### `async setBaseline(eCO2, tvoc)`

保存しておいたベースラインを復元する。**`init()` の後に呼ぶ必要がある**（データシートの指定）。

| 引数   | 型     | 説明                                           |
| ------ | ------ | ---------------------------------------------- |
| `eCO2` | Number | `getBaseline()` で得た `eCO2`。0〜65535 の整数 |
| `tvoc` | Number | `getBaseline()` で得た `tvoc`。0〜65535 の整数 |

範囲外・非整数は例外にする（ガイドの品質チェックリスト「公開セッターに値チェックがあるか」）。

> **⚠ 電文のパラメータ順が逆になっている**
> データシートより:
>
> - `sgp30_get_iaq_baseline` の応答は **(CO2eq, TVOC)** の順
> - `sgp30_set_iaq_baseline` のパラメータは **(TVOC, CO2eq)** の順
>
> 引数・返り値はどちらも **eCO2 を先に統一**し、電文の入れ替えはドライバー内部で吸収する
> （Adafruit の `setIAQBaseline(eco2_base, tvoc_base)` も同じ方針）。
> ここを取り違えると「エラーは出ないのに値がおかしい」というガイド6章の最悪パターンになる。

## 命名の根拠

| 決めたこと             | 選んだもの                         | 理由                                                                                                                 |
| ---------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| read 系メソッド名      | `read()`                           | DRIVER_GUIDE.md 準拠。`adt7410` 等が採用                                                                             |
| 返り値のキー           | `eCO2` / `tvoc` / `h2` / `ethanol` | データシート表記に合わせつつキャメルケース化。`co2` にすると実測 CO2 と誤解されるため `eCO2`（equivalent CO2）を維持 |
| 返り値の形             | 名前付きオブジェクト               | 配列だと順番を間違える。example 側で分割代入できる                                                                   |
| `setBaseline` の引数順 | eCO2 が先                          | `getBaseline()` の返り値順・`read()` のキー順と揃える。電文順（TVOC 先）に引きずられない                             |
| シリアル番号の型       | 文字列                             | 識別子であり演算対象ではない。16進表記のほうが照合しやすい                                                           |

## example のループ形式について（判断を明記）

`setInterval` ではなく **`while (true)` + `await sleep(1000)`** を採用した。

- 理由1: `pizero/src/esm-examples/` の全 example がこの形式（規約準拠）
- 理由2: `read()` が遅延したときに呼び出しが重ならない（ガイド6章「値がたまに化ける」対策）
- トレードオフ: 実周期は `1000ms + read() と readRaw() の所要時間`（約 12 + 25ms）= 約 1.04 秒。
  厳密な 1.000 秒が必要になった場合は経過時間を測って `sleep(1000 - elapsed)` にする

## 調査時の誤りの訂正（2回訂正しています）

ベースラインの「1週間」制約について、次の経過をたどりました。

1. 当初「データシートは1週間以上前のベースライン値の復元を認めていない」と書いた
2. データシート Version 1.0 を確認し、**記載がなかったため撤回した**
3. Sensirion の一次資料を追加確認し、**制約は実在すると再確認した（撤回が誤りだった）**

**確定した事実:** データシートには記載がないが、Sensirion の
[SGP30 Driver Integration Guide][dig] と[公式ドライバー][emb]に明記されている。

| 条件                 | 値                  | 出典の記述                                                                               |
| -------------------- | ------------------- | ---------------------------------------------------------------------------------------- |
| 有効な値が返るまで   | `init()` から約60分 | "A valid baseline value is only returned approx. 60min after a call to sgp30_iaq_init()" |
| 保存してよくなるまで | 12時間の連続運転    | "the sensor has to run for 12 hours until the baseline can be stored"                    |
| 保存の推奨間隔       | 約1時間ごと         | "the current baseline value should be stored approximately once per hour"                |
| 保存値の有効期限     | 最大7日             | "While the sensor is off, baseline values are valid for a maximum of seven days"         |

[dig]: https://files.seeedstudio.com/wiki/Grove-VOC_and_eCO2_Gas_Sensor-SGP30/res/Sensirion_Gas_Sensors_SGP30_Driver-Integration-Guide_HW_I2C.pdf
[emb]: https://github.com/Sensirion/embedded-sgp/blob/master/sgp30/sgp30.h

**教訓:** 「データシートが最終的な正」という原則は正しいが、**データシートに書いていないこと=制約が
存在しない、ではない**。Sensirion のようなメーカーは、実装上の注意をデータシートではなく
Driver Integration Guide 側に書く。データシートで見つからなかった項目は、
統合ガイドと公式ドライバーのソースまで当たる必要がある。

**実装への反映:**

- `setBaseline()` に鮮度チェックは実装しない（ドライバーは保存時刻を知りようがないため、
  アプリケーション側の責任）。範囲チェックのみ
- 制約は `readme_baseline.md` に表として明記した
- `main_baseline.js` は未確立（`0`）を検出して分岐する

## 実機検証で判明した挙動（公式資料に記載のないもの）

Raspberry Pi Zero + M5Stack U088 での実測。5件すべて公式資料に記述がない。

| #   | 挙動                                                                                                                                                               | 設計への影響                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| 1   | 未確立のとき `getBaseline()` は `{ eCO2: 0, tvoc: 0 }` を返す                                                                                                      | `0` を無効判定に使える                          |
| 2   | 有効になるのは `init()` から**16秒後**（統合ガイドは "approx. 60min"）。15秒目まで `0`、16秒目に非ゼロ                                                             | 待ちの上限 60 秒で十分                          |
| 3   | 未確立の間の `setBaseline()` は**受理されるが反映されない**（エラーも出ない）                                                                                      | 未確立の状態では検証不能。待ってから検証する    |
| 4   | ベースライン値は**生信号のティック値ではない**（`0x8e63`/`0x8e1e` = 36451/36382、別セッションでは 38159/39842。生信号の逆算値 13910/19885 との比が一定にならない） | 不透明な値として扱う                            |
| 5   | ベースラインは**短時間では変化しない**（16秒目と46秒目で同値）                                                                                                     | 書き込み→読み戻しの比較が値の更新で誤検知しない |

> #2 について: **非ゼロになったことは「保存してよい」を意味しない。**
> 統合ガイドの「保存には12時間の連続運転が必要」は別条件。16秒で得られる値は暫定値。

## 検証方法の設計変遷（実測により3回作り直した）

| 版         | 方式                                      | 否定された理由                                   |
| ---------- | ----------------------------------------- | ------------------------------------------------ |
| 初版       | 現在値を書き戻す（非破壊）                | 起動直後は両方 `0` で検出力ゼロ（挙動1）         |
| 2版        | 未確立時にプローブ値を書き込む            | 未確立時の書き込みは反映されない（挙動3）        |
| 3版        | 有効化を待ってから現在値を書き戻す        | **書き込みが無視されても一致してしまう**（下記） |
| **確定版** | **有効化を待ち、異なる値のプローブ→復元** | —                                                |

### 3版が抱えていた論理的な穴（自己レビューで発見）

`setBaseline(現在値)` → `getBaseline()` → 現在値、という往復は**必ず一致する**。
`setBaseline()` が無視された場合でも `getBaseline()` はアルゴリズム自身の値
（＝書き込もうとした値と同じ）を返すため。

つまり「書き込みが効いた」と「書き込みが無視された」を区別できていなかった。
実機では 3版のテストが**通った**が、それは正しさの証明になっていなかった。
挙動3で「無視される状態が実在する」ことを観測済みなので、机上の心配ではない。

**教訓:** 往復テストは「書き込む値が現在の状態と異なる」ことが検出力の前提。
同じ値を書き戻す設計は非破壊だが、無反映と区別できない。

### 確定版の検証内容

現在値とは異なる既知の値を一度書き込んで確認し、そのあと元の値に戻す。
1回の実行で3つのことを同時に確認する。

| 判定                 | 条件                                           |
| -------------------- | ---------------------------------------------- |
| パラメータ順の不一致 | プローブが逆順で返る → 例外                    |
| 書き込みの無反映     | プローブ以外の値が返る → 例外                  |
| 復元の成否           | 元の値を書き戻して読み直し、一致しなければ例外 |

プローブ値が有効なのは数十ミリ秒で、直後に元の値へ戻すため実害はない。
モックで3パターン（正常 / デバイスが逆順解釈 / 書き込みを無視）を検証し、
すべて期待どおりに判定することを確認済み。

### 外れた予測の記録

`VALUES_GUIDE.md` で生信号から逆算した基準値（`sref_H2` ≈ 13910 / `sref_E` ≈ 19885）が
そのままベースライン値として保存されているのではないか、と予測したが**外れた**。
実測は 36451 / 36382（別セッションでは 38159 / 39842）で、比が一定にならない。
ベースラインは生信号とは別のエンコードで保持されている。

## 実装しないと決めたもの（見落としではない）

### ベースラインの JSON 保存・復元

`getBaseline()` の値をファイルに保存し、次回起動時に `setBaseline()` で復元する機能は
**意図的に実装しない**。保存・復元こそがこの機能の存在理由なので、
レビューで「なぜないのか」を問われうる点として記録しておく。

| 理由                       | 内容                                                                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 検証できない               | Sensirion の統合ガイドは「保存には12時間の連続運転が必要」と明記。実機で12時間回さないと、正しく機能しているか確認できない。「実機で検証手順を書ける機能だけ実装する」という本件の方針に反する |
| 間違った使い方の実演になる | 現状得られるのは起動15秒後の暫定値。これを保存・復元すると、でたらめな基準で補正することになる                                                                                                 |
| ドライバーの責務外         | ファイル I/O はアプリケーション側の仕事。7日以内の鮮度チェックに必要な保存時刻も、ドライバーは知りようがない                                                                                   |
| example の役割を逸脱する   | `esm-examples` の例は最小限の実演。fs のパス処理やエラー処理を入れると、センサーではなく Node.js のファイル操作の説明になる                                                                    |

代わりに `readme_baseline.md` に、保存時刻を記録して7日以内かを確認するのは
アプリケーション側の責任であることを明記した。

### Set_humidity（湿度補正、`0x2061`）

補正が効いたかを外部から検証できない。絶対湿度への換算式と 8.8 固定小数点の理解コストに対し、
確認できるのは「エラーが出ない」ことだけ。実用には第2センサー（SHT30 等）が必要で、
example が2デバイス構成になってしまう。

### Measure_test（セルフテスト、`0x2032`）

データシートに「`sgp30_iaq_init` の後には使うべきでない」「実行後はスリープモードに入る」と
明記されており、`init()` 内での安全な配置に追加検証が必要。

## 工程5 で決める（＝まだ決めていない）こと

- `sleep` ヘルパーをモジュールレベルの `const`（`scd40/index.js` の実際の書き方）にするか、
  DRIVER_GUIDE の骨格テンプレートどおり `async wait(ms)` メソッドにするか
  → 公開メソッドを増やさずに済む前者を推奨

  `throw new Error(...)` を例示、DRIVER_GUIDE は `console.error` + `return null`。
  **レビューを通す観点ではリポジトリ側（throw）を推奨**
- Feature set の判定条件（Adafruit は `(featureSet & 0xF0) === 0x0020`）を
  データシートの Feature set 章と突き合わせて確定させる
